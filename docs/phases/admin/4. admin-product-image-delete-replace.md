# 4. Admin Product Image Delete and Replace

## 1. Overview

This phase extends the Admin Product Image Management system by adding two important operations:

- Delete an existing product image
- Replace an existing product image

The previous phase implemented product image upload using Cloudinary.

After this phase, the administrator can manage existing product images directly from the Admin Edit Product page without manually accessing Cloudinary or MongoDB.

The complete image-management functionality now supports:

- Upload image
- Display image
- Delete image
- Replace image

---

## 2. Objective

The objectives of this phase are:

- Allow the admin to delete product images.
- Delete the actual image from Cloudinary.
- Remove the corresponding image reference from MongoDB.
- Allow the admin to replace an existing product image.
- Upload the replacement image to Cloudinary.
- Remove the old image from Cloudinary.
- Store the new image URL and public ID in MongoDB.
- Update the frontend immediately after deletion or replacement.
- Provide a simple image-management interface for non-technical administrators.

---

## 3. Existing Image Structure

Product images are stored in MongoDB as objects.

Example:

```js
images: [
  {
    url: "https://res.cloudinary.com/...",
    publicId: "homemade-by-amma/products/002/..."
  }
]
```

Each image contains:

### `url`

Used by the frontend to display the image.

### `publicId`

Used by Cloudinary to identify the image for operations such as:

- Delete
- Replace

The `publicId` is therefore important for image CRUD operations.

---

## 4. Cloudinary Delete Service

File:

```text
server/src/services/cloudinaryService.js
```

The Cloudinary service contains:

```js
async function deleteImage(publicId) {
  if (!publicId) {
    return;
  }

  await cloudinary.uploader.destroy(publicId);
}
```

The function accepts a Cloudinary `publicId` and deletes the corresponding image from Cloudinary.

This keeps Cloudinary-specific logic inside the service layer instead of placing it directly inside controllers.

# PART A — DELETE PRODUCT IMAGE

## 5. Delete Image Requirement

The admin should be able to delete an existing product image directly from:

```text
/admin/products/:productId
```

The deletion must remove the image from both:

```text
Cloudinary
+
MongoDB
```

Deleting only the MongoDB reference would leave an unused image in Cloudinary.

Deleting only the Cloudinary image would leave a broken image reference in MongoDB.

Therefore both operations are required.

---

## 6. Delete Image API

The backend provides:

```http
DELETE /api/products/:productId/images
```

Example:

```http
DELETE /api/products/002/images
```

The request body contains:

```json
{
  "publicId": "homemade-by-amma/products/002/example-image"
}
```

---

## 7. Delete Product Image Controller

File:

```text
server/src/controllers/productController.js
```

Controller:

```text
deleteProductImage
```

The controller performs the following operations:

1. Read `productId` from route parameters.
2. Read `publicId` from the request body.
3. Validate that `publicId` was provided.
4. Find the product using `productId`.
5. Verify that the product exists.
6. Verify that the image belongs to the product.
7. Delete the image from Cloudinary.
8. Remove the image object from `product.images`.
9. Save the updated product in MongoDB.
10. Return the updated image array to the frontend.

---

## 8. Image Ownership Validation

Before deleting an image, the controller checks whether the provided `publicId` exists inside the product.

Conceptually:

```js
const imageExists = product.images.some(
  (image) => image.publicId === publicId
);
```

This prevents the endpoint from deleting an image reference that does not belong to the selected product.

---

## 9. Delete from Cloudinary

After validation, the controller calls:

```js
await deleteImage(publicId);
```

The Cloudinary service performs:

```js
cloudinary.uploader.destroy(publicId);
```

This removes the actual uploaded image from Cloudinary.

---

## 10. Delete from MongoDB

After deleting the Cloudinary image, the corresponding image object is removed from the product.

Conceptually:

```js
product.images = product.images.filter(
  (image) => image.publicId !== publicId
);
```

The product is then saved:

```js
await product.save();
```

MongoDB therefore no longer contains the deleted image reference.

---

## 11. Delete Route

File:

```text
server/src/routes/productRoutes.js
```

The delete route is:

```js
router.delete(
  "/:productId/images",
  protect,
  adminOnly,
  deleteProductImage
);
```

The route is protected so that product image deletion is an admin operation.

The frontend tracks the image currently being deleted.

Conceptually:


While deletion is running, the button displays:

```text

```

This prevents repeated delete requests for the same image.

# PART B — REPLACE PRODUCT IMAGE

## 15. Replace Image Requirement

The administrator should also be able to replace an existing image without manually performing:

```text
Delete old image
+
Upload new image
```

Instead, the admin can select a replacement image and perform both operations through a single action.

---

## 16. Replace Image API

The backend provides:

```http
PATCH /api/products/:productId/images
```

Example:

```http
PATCH /api/products/002/images
```

The request uses:

```text
multipart/form-data
```

It contains:

```text
image    → new image file
publicId → public ID of the existing image
```

---

## 17. Replace Product Image Controller

File:

```text
server/src/controllers/productController.js
```

Controller:

```text
replaceProductImage
```

The controller performs the following operations:

1. Read `productId`.
2. Read the existing image `publicId`.
3. Verify that a replacement file was uploaded.
4. Verify that `publicId` was provided.
5. Find the product.
6. Find the existing image inside `product.images`.
7. Upload the new image to Cloudinary.
8. Delete the old image from Cloudinary.
9. Replace the old MongoDB image object with the new image information.
10. Save the product.
11. Return the updated images to the frontend.

---

## 18. Finding the Existing Image

The controller identifies the exact image using its Cloudinary `publicId`.

Conceptually:

```js
const imageIndex = product.images.findIndex(
  (image) => image.publicId === publicId
);
```

If the image cannot be found, the backend returns an image-not-found response.

---

## 19. Uploading the Replacement Image

The replacement file is received through Multer:

```text
req.file
```

It is uploaded using the existing Cloudinary service:

```js
uploadImage(
  req.file.buffer,
  `homemade-by-amma/products/${product.productId}`
);
```

Cloudinary returns a new:

```text
url
publicId
```

---

## 20. Removing the Old Cloudinary Image

After the replacement image is uploaded successfully, the old image is removed using:

```js
await deleteImage(publicId);
```

This prevents old, unused images from remaining in Cloudinary.

---

## 21. Updating MongoDB

The existing image entry is replaced with the new Cloudinary information.

Conceptually:

```js
product.images[imageIndex] = {
  url: uploadedImage.url,
  publicId: uploadedImage.publicId,
};
```

The product is then saved.

The result is:

```text
Old URL + Old publicId
          ↓
       replaced
          ↓
New URL + New publicId
```

---

## 22. Replace Route

File:

```text
server/src/routes/productRoutes.js
```

The route uses:

```js
router.patch(
  "/:productId/images",
  protect,
  adminOnly,
  upload.single("image"),
  replaceProductImage
);
```

Multer processes the replacement image before the controller runs.

---

## 23. Frontend Replace API

File:

```text
client/src/lib/api/products.js
```

The frontend provides:

```text
replaceProductImage(productId, publicId, file)
```

It creates a `FormData` object containing:

```js
formData.append("publicId", publicId);
formData.append("image", file);
```

The request uses:

```http
PATCH /api/products/:productId/images
```

The browser automatically creates the correct multipart `Content-Type` boundary.

Therefore `Content-Type` is not manually specified.

---

## 24. Multiple Images and Replacement State

A product can contain multiple images.

For example:

```js
images: [
  {
    url: "...",
    publicId: "image-1"
  },
  {
    url: "...",
    publicId: "image-2"
  }
]
```

Because every image can have its own replacement file, one shared replacement-file state is not sufficient.

The frontend therefore stores replacement files using the image `publicId`.

Conceptually:

```js
const [replacementFiles, setReplacementFiles] = useState({});
```

Example state:

```js
{
  "image-public-id-1": File,
  "image-public-id-2": File
}
```

This allows each image card to manage its own replacement selection.

## 34. Important Difference Between Upload and Replace

### Upload Image

Upload adds another image:

```text
Before:

images = [Image A]

After Upload:

images = [Image A, Image B]
```

### Replace Image

Replace changes one existing image:

```text
Before:

images = [Image A, Image B]

Replace Image A with Image C

After:

images = [Image C, Image B]
```

This distinction is important for both implementation and administrator usability.

Cloudinary API credentials remain exclusively on the backend.

The frontend never receives the Cloudinary API secret.
